# M2b local validation, 2026-10-09

A CI-built war (`593ad663cd`) ran locally with `KESTREL_STORAGE=dynamodb` against DynamoDB Local
(`scripts/kestrel/local-run.sh`). Classes not yet migrated stayed on H2.

`scripts/kestrel/local_validate_m2b.py` passed **18/18** checks:
- form login;
- API token minted and used (indexed lookup);
- project create, list, config read and update, delete (Project + Storage);
- key storage store, list and delete;
- webhook create, list and invoke (through its own token);
- an ad-hoc execution in a DynamoDB-stored project, with the execution itself in H2;
- the rows were checked directly in the DynamoDB tables.

**Restart:** a project config and a key written before a full JVM restart read back unchanged
afterwards.

Tables created on demand: `local-project`, `local-user`, `local-auth_token`, `local-storage`,
`local-webhook`, `local-plugin_meta`, `local-stored_event`, `local--index` and `local--ids`.

## Fixes found by running the app (all in the datastore)

| Symptom | Cause | Fix |
|---|---|---|
| "No Datastore Session bound to thread" on event threads and API calls | GORM's generic datastore will not open sessions on demand | Open plain sessions on demand |
| "No value for key [DynamoDatastore] bound to thread" on rollback | The on-demand session joined Hibernate's transaction synchronization | On-demand sessions stay unbound |
| Ad-hoc execution stuck in `running` | Quartz `ExecutionJob` uses `@Transactional` outside Spring; GORM's single-datastore lookup became ambiguous | The DynamoDB datastore leaves that lookup to Hibernate |
| Classes with `mapWith = 'dynamodb'` rejected | GORM's key-value mapping context only accepts `keyvalue` | Added `DynamoMappingContext` |

Each fix has a spec in `DynamoDatastoreSpec` (12 specs).

EKS validation of M2b runs together with the remaining M1 items.
