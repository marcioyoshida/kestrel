# M2d: no RDBMS, and upstream's API suite on DynamoDB, 2026-10-11

With `storage.mode: dynamodb` Kestrel now runs with **no database server**. Every domain class is
stored in DynamoDB. The Hibernate plugin stays, because upstream services are `@Transactional`
through its transaction manager, but it maps no class. Its datasource is a private in-memory H2
with no schema and with Liquibase off, so a leftover SQL query fails instead of reading shared
data. Bootstrap fails if any domain class is not stored in DynamoDB. Readiness checks DynamoDB.
The reference stack creates RDS only with `-c rdbms=true`.

Final image: `kestrel:1ea9571fae59` (commit `1ea9571fae`).

## Found by the API suite and fixed (each with a spec; 28 pass)

1. **GORM validation never ran for DynamoDB classes.** GORM's key-value base sets no validator
   registry, so `validate()` always returned true. The datastore now creates the registry and
   registers GORM's generic `unique` constraint (Hibernate registers its own). Three bugs came
   from this:
   - importing an archive into a second project duplicated job uuids, and the import then hit a
     write conflict;
   - "create the same job twice" succeeded;
   - an option with an invalid `valuesUrl` was accepted.
2. **Every job run rewrote the job.** Saving an execution adds it to the job's loaded
   `executions` collection, and the dirty check counted that as a change to the job. Concurrent
   scheduled firings then conflicted ("Unable to start Job execution: The instance was updated by
   another user"). The many side of a bidirectional one-to-many no longer counts as a change to
   its owner, as with Hibernate's inverse collections.
3. **A retry was visible before its link.** On DynamoDB every flush is visible at once. The retry
   execution's `save(flush: true)` also wrote the failed execution as `failed-with-retry` before
   `retryExecution` was set. On DynamoDB the retry now starts in its own session.

Ported in the first commit (`05dc8ad81a`): the Hibernate-only sites still reachable with no
RDBMS:
- the job-list run-later and scheduled filter (`Restrictions`/`Subqueries`);
- the job forecast's run-later executions (HQL);
- execution cleanup (HQL);
- `createAlias` in job-state and takeover;
- the JDBC takeover query.

## Still open

- **Sorted indexes for executions and reports.** Lists filter in memory over candidates the
  indexes have narrowed, which is fine at reference scale.
- **Intermediate flushes are visible at once.** Unlike Hibernate inside a transaction, every
  flush is visible to other pods immediately. The retry case is fixed; others may exist where
  upstream flushes mid-transaction.
